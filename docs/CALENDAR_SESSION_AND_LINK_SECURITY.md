# Calendar session data and matter links

Calendar event payloads are no longer persisted in sessionStorage. Loading the calendar uses the current authenticated matter-only feed, followed by the current CalDAV feed. This trades immediate cached display for a fresh request. Legacy cache entries are removed when the cleanup module loads and at login/logout, session expiry and account transitions. Visible calendar events are cleared on session boundaries; request generations discard earlier event responses. Calendar-list responses also check a session epoch, and unmount invalidates pending work.

Matter links are verified on the server. A supplied reference must identify a resource on the configured internal Radicale server; canonicalization prevents URL aliases bypassing conflict checks and prevents arbitrary remote requests. The actor must have matter access (the route check) and own or hold a write share on the target calendar. The target resource must exist. Calendar/share row locks and a partial unique index prevent conflicting verified links. Read-only shares and public subscriptions do not confer link rights. Removing a link is a matter metadata operation and does not modify the remote appointment.

Calendar titles always come from the calendar entry. A verified matter link adds matter metadata, but cannot replace the calendar title with a matter event name. Actual calendar edits continue through the existing calendar write-permission checks. Renaming a matter event alone cannot change the calendar's displayed title.

Migration feabd2e3f4a5 adds calendar_link_verified, default false, and uniqueness for verified non-null references. Historical references are retained for review, not silently trusted or deleted. Until reviewed, they do not supply calendar metadata or suppress the standalone matter event. The event API hides the unverified synchronization reference and reports calendar_link_needs_review; frontend synchronization skips it and the matter Events screen reports the pause. No remote appointment is rewritten, deleted or recreated by the migration.

Before resuming an existing link, a calendar owner/editor with matter access must inspect the historical reference and confirm the intended appointment. Re-submit that reference through PATCH /cases/{case_id}/events/{event_id} with calendar_event_uid; server authorization, existence and conflict checks run again. To disconnect it without changing the remote appointment, PATCH calendar_event_uid to null. Historical raw references remain in case_event for controlled administrative review; there is no automatic trust backfill or bulk verification. A dedicated review UI is not included in this change. Pending links can appear as separate matter and calendar entries until review resolves their relationship.

Tests include PostgreSQL authorization and concurrent duplicate-link attempts, historical reference handling, invalid remote URLs, browser storage/session boundaries and late responses, and blocked synchronization of unverified links. Isolated integration additionally exercises real Radicale lookup, personal calendars, GUI sharing/subscriptions, title integrity, duplicate rejection and revocation. A migration probe seeds duplicate references before the upgrade, then confirms retention as untrusted and database uniqueness for verified links.
