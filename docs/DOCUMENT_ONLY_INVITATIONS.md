# Document-only invitations

Sending or resending a Canary Sign request, quote or form no longer creates or re-enables ContactPortalAccess, assigns an access code, or changes general portal grants. The former automatic provisioning helper has been removed. Notification rendering strips access_code from these document workflows, including custom-template input. Explicit portal account administration and ordinary portal login remain separate.

A signing recipient must be a contact on the matter. If both contact_id and case_contact_id are supplied they must identify the same matter contact. The delivery address comes from that matter contact (falling back to the stored contact card when the snapshot has no address); a different address supplied in the send body is rejected. Unlinked or foreign contacts, inconsistent IDs and duplicate contact recipients are rejected before preparing artifacts. The staff UI selects a matter contact and treats the resulting name/email as read-only. Quotes and forms recheck membership on both send and resend.

Invitation exchanges create document-scoped sessions, not general portal login sessions. Quotes/forms use signed version-2 invitations bound to kind, resource, contact, matter, matter-contact row, email and send generation. Signing exchanges use a similarly scoped invitation bound to the exact recipient and its current random signing token. Authorization checks the invitation again at read/mutation boundaries. Only the intended document can be viewed or completed; unrelated forms, quotes, signing requests, folder grants, downloads and uploads remain inaccessible. Existing ordinary portal sessions continue to use their existing permissions.

No portal account is required. When an account already exists, its state is captured for conservative revocation: changes such as disabling, expiry, code reset or version rotation invalidate earlier invitations. Sending a fresh document to a contact whose portal account is already disabled or expired does not enable it. A change in portal-account state may therefore require a fresh invitation. The binding carries a keyed digest, never the access-code hash itself.

Resends change the send generation/token and invalidate earlier invitations and their document sessions. Recipient removal, email changes, matter blocks, disabled firm/matter features, request expiry and inactive document statuses are rechecked. Completed documents remain readable through the already-issued scoped session where supported, but completed invitations cannot create new sessions. Signing dispatch rechecks the queued message against the current recipient and binding, and locks recipient authority during the final delivery check/provider call. No new background scheduling is introduced.

Migration feace3f4a5b6 adds a nullable signing-invitation binding. Historical signing links and queued messages are not trusted automatically: they require a validated resend. Old queued bodies cannot bypass the new binding requirement. Existing correctly scoped form/quote invitations retain their original portal-version checks for compatibility; new sends/resends use the document-only model.

Existing portal accounts and grants are not deleted or disabled by this migration. In particular, previously auto-provisioned accounts and previously emailed access codes need separate historical review; this change does not claim to revoke those credentials retrospectively. A recipient email change requires a corrected signing request rather than silently redirecting an existing one.

Validation uses migrated PostgreSQL, real synthetic document generation, production HTTP routes and captured/fake notification transports. Regression coverage includes no-account, disabled-account and active-account send/resend/completion; account-state preservation; recipient substitution; resource isolation; changed/removed recipients; queued delivery eligibility; legacy invitation rejection; existing portal revocation and preview boundaries. Frontend tests cover all three send dialogs. No live providers or production data are needed.
